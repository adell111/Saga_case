# Интеграция с внешними сервисами (эмуляция) — кейс 2

## Как заполнять

В кейсе два внешних сервиса: БКИ и СМЭВ. Сервис БКИ — готовый образец (его трогать не нужно).
СМЭВ, логирование и поведение при таймаутах вам нужно заполнить самостоятельно.
По вашему описанию должно быть понятно, как программисту реализовать эмуляторы.

\---

## 1\. БКИ (Бюро кредитных историй) — ОБРАЗЕЦ (не трогать)

**Назначение:** получить кредитный скор, флаг просрочки, число запросов за 90 дней.

**Контракт запроса:**

```json
POST /bki/score
{
  "passport\\\_hash": "a1b2c3d4e5f6a7b8"
}
```

**Контракт ответа (успех):**

```json
{
  "score": 720,
  "delinquency": false,
  "requests\\\_90d": 1
}
```

**Правила эмуляции (детерминизм):**

* Взять `h = int(hashlib.md5(passport\\\_hash.encode()).hexdigest(), 16) % 10`.
* Если `h <= 5` → `score` = 600 + h\*20 (600–700), `delinquency` = false.
* Если `6 <= h <= 8` → `score` = 450 + (h-6)\*50 (450–550), `delinquency` = false.
* Если `h == 9` → `score` = 400, `delinquency` = true.
* `requests\\\_90d` = 1 (фиксировано).

**Таймаут:** 3 секунды. При превышении — вернуть `TIMEOUT`.

\---

## 2\. СМЭВ (Система межведомственного электронного взаимодействия)

**Назначение:** проверить соответствие паспортных данных клиента (по `client_id` и `passport_hash`), то есть подтвердить, что за заявкой стоит реальный клиент с такими данными.

**Контракт запроса:**

```json
POST /smev/check
{
  "client_id": "cli_0001",
  "passport_hash": "f727a849055f2224"
}
```

**Контракт ответа (успех):**

```json
{
  "status": "MATCH"
}
```

Допустимые значения `status`: `MATCH` (данные совпали), `MISMATCH` (не совпали), `TIMEOUT` (нет ответа вовремя), `NOT_CALLED` (до вызова не дошли, например заявка отсеяна на валидации).

**Правила эмуляции (детерминизм):**

* Взять `h = int(hashlib.md5(client_id.encode()).hexdigest(), 16) % 10`.
* Если `h == 0` → `status` = `MISMATCH` (в среднем одна заявка из десяти).
* Иначе → `status` = `MATCH`.
* `status` = `TIMEOUT` — если эмулятор «спит» > 3 секунд. В прототипе таймаут включается явно для выбранных клиентов флагом `--timeout-clients cli_0003,cli_0011`; без флага таймаутов нет, поэтому результат прогона воспроизводим. `random` не используется, `hash()` тоже (он меняется от запуска к запуску).

**Таймаут:**
3 секунды, один повтор через 0,5 с. При превышении (после повтора) эмулятор возвращает `TIMEOUT`, решение конвейера — `NEED_MORE_DATA` с reason `EXTERNAL_TIMEOUT`.

**Фактическая раскладка эмулятора БКИ в прототипе** (по образцу из раздела 1, без изменений): `h <= 5` → 600 + h·20 (600…700), без просрочки; `6 <= h <= 8` → 450 + (h−6)·50 (450…550), без просрочки; `h == 9` → 400 и просрочка. Колонка `bki_score` в `applications.csv` получена не этим эмулятором, поэтому для отдельных заявок значения расходятся (см. `03_тесты.md`). Для сверки есть режим `--use-csv-external`.

## 3\. Логирование вызовов (audit)

Каждый вызов внешнего сервиса (включая каждую попытку повтора) записывается в файл `external.log`, одна JSON-строка на вызов. Персональных данных в журнале нет: ни паспорта, ни ФИО, ни дохода.

| Поле | Пример | Зачем нужно |
| --- | --- | --- |
| timestamp | 2025-11-01T10:00:00Z | когда был вызов; нужно, чтобы собрать хронологию инцидента и сопоставить вызов с событием аудита |
| service | BKI | какой сервис вызывали (BKI или SMEV); видно, какой из двух источников сбоит |
| request_id | req_0001 | уникальный номер запроса (`req_NNNN`); связывает строку журнала с конкретным вызовом и позволяет разбирать его отдельно |
| status | SUCCESS | итог вызова: SUCCESS / TIMEOUT / ERROR; по доле TIMEOUT видно деградацию сервиса |
| latency_ms | 120 | задержка в миллисекундах; позволяет проверить выполнение NFR о 3 секундах и заметить замедление |
| result | {"score": 720} | краткий результат (`{"status": "MATCH"}`, `{"score": 720, "delinquency": false}`); объясняет решение без обращения к самому сервису |

Журнал только дописывается (append-only). Связь с аудитом решений: событие `decision_made` в `audit.log` относится к тем же `app_id`, а таймаут в `external.log` объясняет reason `EXTERNAL_TIMEOUT` в решении.

## 4\. Поведение при таймауте

1. Что возвращает эмулятор при таймауте? — `TIMEOUT` (в журнал пишется `status=TIMEOUT`, `latency_ms=3000`).
2. Какое решение принимает кредитный конвейер? — `NEED_MORE_DATA`. Не `REFUSED` и тем более не `APPROVED`: пока данные не проверены, ни отказывать, ни одобрять автоматически нельзя.
3. Какой reason записывается в итоговое решение? — `EXTERNAL_TIMEOUT`.
4. Можно ли повторить запрос к внешнему сервису? — да, один раз через 0,5 с (обе попытки пишутся в `external.log`). Если повтор тоже не удался, решение `NEED_MORE_DATA`; клиент может подать заявку позже, и тогда сервис вызовет эмулятор заново.
5. Что видит клиент на экране своего приложения? — «Не удалось проверить данные, попробуйте позже» (текст из `08_reasons.md`; в интерфейсе можно показать как «Проверяем данные, попробуйте позже»).

## 6\. Типичные ошибки (минус баллы)

1. **Эмулятор недетерминирован** (используется `random` без seed) — тесты невозможно воспроизвести.
2. **Нет таймаута** — сервис «зависает» при сбое сети.
3. **Таймаут приравнен к отказу** — клиент получает `REFUSED` вместо `NEED\\\_MORE\\\_DATA`.
4. **Нет логирования** — невозможно разобрать инцидент.
5. **СМЭВ описан без `client\\\_id`** — непонятно, чьи данные проверяются.
